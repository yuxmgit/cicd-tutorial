# 第 20 章 从单机到集群的演进信号

> 难度：★☆☆　预计耗时：40 分钟（了解为主，不实操）
> 本章目标：回答"什么时候这台单机不够用了、要不要上 K8s"。**结论先行：不要因为"高级"而迁移，只在出现明确信号时迁移，并且每次只解决一个信号。**

---

## 一、为什么需要这一章

技术圈有两个常见错误方向：

- **过早上 K8s**：3 人团队、单服务，为了简历好看搭一套集群。结果：K8s 运维成本（学习+排障+升级）超过业务本身，一个小团队花一半时间维护"平台"。
- **死撑单机**：服务已经多到 compose 文件 800 行、发布靠人肉记顺序、机器 90% 内存常驻，还在说"再撑撑"。

正确的判断依据是**信号**，不是潮流。本章给出信号清单、单机方案的能力边界、以及真要迁移时的路径。

---

## 二、原理图解：单机方案的能力边界

```mermaid
flowchart LR
    subgraph OK["单机方案（本书）能覆盖"]
        A1["1~5 个服务"]
        A2["日活数千级别流量"]
        A3["单实例即可承载"]
        A4["偶发分钟级停机可接受"]
        A5["1~2 人维护基础设施"]
    end
    subgraph SIGNAL["出现即考虑演进"]
        S1["🔴 单机资源长期 >70%"]
        S2["🔴 高可用要求：不能接受停机"]
        S3["🔴 服务 >10 个，依赖图复杂"]
        S4["🔴 需要自动扩缩容"]
        S5["🔴 多团队抢发布窗口"]
    end
```

**核心原则：单机的瓶颈先被"加机器跑同一套方案"缓解（垂直扩展 + 拆分部署目标），再被"编排平台"解决（水平扩展 + 自动化）。**

很多团队跳过了中间步骤：一台不够 → 直接 K8s。其实"一台构建机 + 两台生产机 + Nginx 手动分流"就能把容量翻一倍，成本和复杂度远低于集群。

## 三、五种演进路径（按成本从低到高）

| 路径 | 做法 | 解决什么 | 成本 | 不解决什么 |
| --- | --- | --- | --- | --- |
| ① 单机加大 | 4C8G、加数据盘 | 资源型瓶颈（内存/磁盘/CPU） | 低（云控制台点几下） | 高可用、规模化发布 |
| ② 前后端分机 | 前端静态走 CDN/对象存储，后端独立 ECS | 2M 带宽瓶颈（本项目最该先做的！） | 低 | 后端单点 |
| ③ 双机 + 手动分流 | 两台生产机 + 云 LB / Nginx upstream | 高可用雏形 | 中 | 自动故障转移的精细度 |
| ④ 多机 + Docker Swarm/Nomad | 轻编排 | 多机调度、滚动发布 | 中 | 生态与人才市场 |
| ⑤ K8s + GitOps | 集群 + Argo CD | 自动扩缩、声明式发布、大规模协作 | 高 | ——（只要维护得起，都能解决） |

> **针对本项目的特别提示**：这台机器的最大瓶颈其实是 **2M 带宽**，而不是 CPU/内存。路径②（前端产物放腾讯云 COS + CDN，后端继续单机）就能把首屏速度提高一个量级，成本每月几块钱。**这也是"先解决最痛的信号"的最佳示范。**

## 四、K8s 与 GitOps 到底解决什么（认知版）

不实操，只建立正确预期：

| 概念 | 单机等价物 | K8s 版本 | 真实收益 |
| --- | --- | --- | --- |
| Deployment | `restart: unless-stopped` | 期望副本数声明 + 自动重建 | 自愈更强、可滚动 |
| Service | `ports:` + Nginx upstream | 虚拟 IP + 负载均衡 | 服务发现自动化 |
| Ingress | `deploy/nginx/site.conf` | 声明式路由 + TLS | 多服务路由统一管理 |
| ConfigMap / Secret | `.env` + 600 权限文件 | 声明式配置对象 | 配置版本化、审计 |
| HPA | 无（人工加机器） | 自动扩缩容 | 流量波峰自动化 |
| GitOps（Argo CD） | `deploy.sh` 推模式 | 拉模式：集群对比 Git 声明，偏差自动纠正 | 环境状态 = Git 状态，漂移可见 |

**GitOps 与本书 `deploy.sh` 的哲学差异**（一句话讲透）：

- 推模式（本书）：CI 说"我要把 42-a1b2c3d 装上去"，服务器被动接受。
- 拉模式（GitOps）：Git 仓库声明"生产应该跑 42-a1b2c3d"，集群里的 Argo CD 持续比对，发现不一致就拉齐。

**推→拉的真正好处**：生产状态永远可以在 Git 里审计（谁改的、什么时候改的、改成什么），"配置漂移"这种病从机制上消失。**代价**：多一套持续运行的 GitOps 组件，以及"紧急操作必须走 Git 提交"的纪律。

## 五、迁移检查表（真要走这条路时）

```text
[ ] 前置：是否已先做路径①②③？（便宜的先做完）
[ ] 团队：至少 1 人能独立维护集群（不是"看过文档"）
[ ] 预算：控制面 + 节点 + 存储 + 备份，通常 ≥ 3 台机器的钱
[ ] 应用改造清单：
    - 无状态化：SQLite → PostgreSQL（多副本下 SQLite 不可用）
    - 配置：.env → ConfigMap/Secret
    - 健康：/healthz 已有（本项目现成 ✅）
    - 日志：文件 → stdout（采集器收集）
[ ] 迁移顺序：先迁无状态前端 → 再迁后端 → 数据库最后 + 双写观察
[ ] 回退方案：单机方案保留 1 个月，随时可切回
```

> 注意第 3 行：**SQLite 是单机方案的最大"锁"**。第 14 章说过它的边界——一旦决定上多副本，第一件事是换 PostgreSQL，这往往比引入 K8s 本身工作量更大。先想清楚。

## 六、坑与误区

| 误区 | 真相 |
| --- | --- |
| "上了 K8s 就不用做监控告警了" | 反了：K8s 系统本身也需要监控，复杂度只增不减 |
| "K8s 能自动回滚所以不用健康检查" | 探针就是回滚的依据，质量差照样滚错方向 |
| "Docker Swarm 已死不能学" | 3 节点以内的小集群，Swarm 依然是"最省心"的编排，第 14 章的 compose 知识几乎全部复用 |
| "GitOps 要先把所有配置搬进 Git 才能上线" | 渐进迁移：先应用配置，再基础设施（IaC），分三个月做 |
| "单机=不专业" | 大量真实业务（日活百万级）跑在单机 + 良好流水线上；架构服务于业务约束 |

### 练习

**练习 1**：本项目现在最值得做的一项演进是什么？给出理由与实施要点。
<details><summary>参考要点</summary>

路径②：前端静态产物放 COS + CDN。理由：机器内存（3.6G）、CPU（4 核）都宽裕，唯一硬瓶颈是 2M 公网带宽；静态资源出 CDN 后，Nginx 只剩 API 反代，首屏速度提升明显，且完全不影响现有部署架构。实施：Vite 产物发布到 COS，Nginx 加一条静态资源 302/或前端直接引用 CDN 域名。
</details>

**练习 2**：团队说"直接上 K8s，一步到位"。你如何反驳或支持？给出决策树。
<details><summary>参考要点</summary>

决策树：服务数 >10 或有明确多副本需求？→ 是则考虑；团队有 K8s 运维能力？→ 否则先 Swarm/双机；预算 3 台机器起？→ 否则单机加大 + 分机。若三条都不满足，K8s 只会增加故障面。支持 K8s 的合理场景：多团队共用发布平台、频繁扩缩容、强合规审计需求。
</details>

**练习 3**：推模式（deploy.sh）在什么情况下会"说谎"？
<details><summary>参考要点</summary>

服务器上有人手工改过容器/配置（漂移），CI 认为部署成功但实际状态与声明不符；或部署脚本中途失败但未失败退出（没 set -e）。拉模式通过持续比对消除漂移；推模式要靠"部署后验证"（第 15 章健康检查 + 第 18 章监控）弥补。
</details>

## 全书结语

回到第 01 章那个手动部署两小时的小张。现在他：

- `git push` 后 3 分钟自动上线，测试、扫描、体积门禁全程把关；
- 坏版本上线 30 秒内自动切回旧版，用户无感知；
- 任何一次发布都能在台账里查到"谁、何时、哪个镜像、批不批得出来"；
- 服务器挂了 5 分钟内群里收到告警，备份每晚自动验证。

**CI/CD 的终点不是工具，而是"发布这件事不再需要勇气"。** 祝部署顺利，回滚永不需要。
