# 第 09 章 质量与安全门禁

> 难度：★★☆　预计耗时：70 分钟
> 本章目标：建立一套"拦得住、跑得快、不误伤"的门禁体系——提交前拦低级错误，CI 里拦质量倒退，镜像里拦高危漏洞，部署前拦明文密钥。

---

## 一、为什么需要这一章

先说三个"门禁失败"的真实故事：

**故事 1：门禁太晚。** 团队只在合并前跑 lint，结果每个人平均要来回改 3 次。因为格式错误（少个分号、多行空行）是最低级的错误，却在最贵的环节被发现。**修一行代码 → 推 → 等 5 分钟 → 报错**，一天浪费两小时。

**故事 2：门禁太假。** 要求"覆盖率 100%"，于是大家写：

```javascript
it('占位测试', () => {
  expect(1).toBe(1)
})
```

覆盖率上去了，bug 一个没少。门禁变成了数字游戏。

**故事 3：门禁缺席。** 某项目引入了一个有已知 RCE 漏洞的旧版依赖，三个月后服务器被挖矿。查日志发现：漏洞在引入的当天就能被扫描出来，但流水线里根本没有"依赖漏洞扫描"这一步。

> 这一章的核心不是"装几个工具"，而是三件事：**把门禁放在最便宜的位置**、**让阈值有依据**、**让豁免有记录**。

## 二、原理图解：四层门禁，越早越便宜

```mermaid
flowchart LR
    A["写代码<br/>（本地）"] -->|第 0 层：编辑器<br/>格式化/语法提示| B["git commit"]
    B -->|第 1 层：提交钩子<br/>lint-staged / 密钥扫描| C["git push"]
    C -->|第 2 层：CI<br/>lint + 单测 + 覆盖率 + 依赖扫描| D["构建镜像"]
    D -->|第 3 层：镜像扫描<br/>Trivy HIGH/CRITICAL| E["部署前<br/>密钥 + SBOM + 审批"]
    E --> F["上线"]

    style A fill:#1e3a8a,color:#fff
    style B fill:#1e40af,color:#fff
    style C fill:#1d4ed8,color:#fff
    style D fill:#2563eb,color:#fff
```

**成本对照（行业经验值）**：

| 发现问题的地方 | 修复耗时 | 说明 |
| --- | --- | --- |
| 编辑器里 | 10 秒 | 保存时自动格式化 |
| 提交钩子 | 30 秒 | 只检查改动的文件 |
| CI 流水线 | 5~15 分钟 | 要重新推、重新等 |
| 测试环境 | 半天 | 要重新部署、重新验证 |
| 生产环境 | 几天 + 信誉损失 | 可能还要写事故报告 |

> **结论：能在左边拦的，绝不留到右边。** 但也不能所有检查都放本地——本地可以被绕过（`--no-verify`），CI 才是最终裁决。

## 三、动手步骤

### 步骤 1 第 1 层：提交前钩子（只检查改动文件）

**前端（husky + lint-staged）**：

```powershell
cd demos\frontend
npm install -D husky lint-staged
npx husky init
```

`package.json` 里加：

```json
{
  "scripts": {
    "prepare": "husky || true",
    "lint-staged": "lint-staged"
  },
  "lint-staged": {
    "*.{js,vue}": ["eslint --fix"],
    "*.{css,md,json}": ["prettier --write"]
  }
}
```

`.husky/pre-commit` 内容：

```bash
#!/usr/bin/env sh
cd demos/frontend && npx lint-staged
```

> `prepare: "husky || true"` 里的 `|| true` 是为了在 CI 环境（没有 git hooks 目录权限）时不报错。

**后端（pre-commit 或简单 shell 钩子）**：

Python 生态推荐 `pre-commit` 框架，`.pre-commit-config.yaml`：

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.4
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: check-added-large-files
        args: [--maxkb=1024]
      - id: detect-private-key
```

```powershell
pip install pre-commit
pre-commit install
```

**注意**：钩子是"礼貌性"的，可以 `git commit --no-verify` 绕过。所以第 2 层必须存在。

### 步骤 2 第 2 层：CI 里的质量门禁

| 检查项 | 工具 | 阻断条件 | 耗时 |
| --- | --- | --- | --- |
| 代码规范 | ESLint / ruff | 有 error | 10~30s |
| 单元测试 | vitest / pytest | 有失败 | 20~60s |
| 覆盖率 | vitest --coverage / pytest-cov | 低于阈值 | 同上 |
| 依赖漏洞 | npm audit / pip-audit | 有 HIGH/CRITICAL | 20~60s |
| 明文密钥 | gitleaks | 发现疑似密钥 | 5~20s |

本项目已备好统一脚本：

```bash
bash scripts/security-scan.sh deps      # 前端 + 后端依赖扫描
bash scripts/security-scan.sh secrets   # 明文密钥扫描
bash scripts/security-scan.sh image cicd-demo-backend:42
```

脚本设计要点（为什么这么写）：

1. **`--audit-level=high`**：只拦高危，不拦低危噪音，否则每天几十条 warning，很快没人看。
2. **`--ignore-unfixed`**（Trivy）：只报"有修复方案"的漏洞，否则基础镜像的已知无解漏洞会永远让流水线变红。
3. **`--redact`**（gitleaks）：命中的密钥不会打印到日志里，避免"扫描工具自己泄露密钥"。
4. **`SOFT=1`**：本地开发机没装工具时跳过，CI 里必须装（不给跳过机会）。

### 步骤 3 阈值怎么定才有依据（别拍脑袋）

**覆盖率阈值用"基线法"**：

1. 先跑一次，看当前真实覆盖率，比如 63%。
2. 把阈值设为 **当前值 - 2%**（61%），保证不会立刻失败。
3. 每次迭代把阈值 +2%，直到 80% 左右停下。
4. 对**新代码**用更严的标准（SonarQube 的 "Coverage on New Code ≥ 80%"）。

**为什么不上来就 100%**：

- 100% 覆盖不代表没有 bug（断言质量才是关键）。
- 逼着写假测试，比不写测试更糟——它会给你虚假的安全感。
- 前端 UI 分支（各种 hover/loading 态）根本不可能 100%。

**本书的取值**：

| 项目 | 起步 | 目标 | 理由 |
| --- | --- | --- | --- |
| 前端 | 50% | 80% | 组件测试成本较高 |
| 后端 | 80% | 85% | 业务逻辑集中，容易测 |

### 步骤 4 第 3 层：镜像漏洞扫描

```bash
# 安装 trivy（Linux/macOS；Windows 用 scoop install trivy 或下载 exe）
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh -s -- -b /usr/local/bin

# 扫描
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 cicd-demo-backend:42
```

输出示例：

```text
cicd-demo-backend:42 (debian 12.9)
==================================
Total: 3 (HIGH: 2, CRITICAL: 1)

┌──────────────┬────────────────┬──────────┬───────────────┬───────────────┐
│   Library    │ Vulnerability  │ Severity │ Fixed Version │    Title      │
├──────────────┼────────────────┼──────────┼───────────────┼───────────────┤
│ libssl3      │ CVE-2026-XXXXX │ CRITICAL │ 3.0.16-1~deb12│ 缓冲区溢出     │
└──────────────┴────────────────┴──────────┴───────────────┴───────────────┘
```

**怎么修**（按优先级）：

1. **升级基础镜像**：`python:3.11-slim` → `python:3.11-slim-bookworm`（或更新的 patch 版本），大部分漏洞随之消失。
2. **升级依赖**：`pip install --upgrade 包名`。
3. **确实没有修复方案**：加入 `.trivyignore`，写清原因和复查日期。

`.trivyignore` 规范：

```text
# CVE-2026-XXXXX: 仅在使用 XX 功能时触发，本服务未使用；2027-01-31 复查
CVE-2026-XXXXX
```

> **不写日期的忽略等于永久忽略。** 三个月后没人记得为什么忽略它。

### 步骤 5 SonarQube：需要就装，不需要别硬上

**先说结论**：本书主线**不装** SonarQube，原因很实在：

| 项 | SonarQube 要求 | 我们的服务器 |
| --- | --- | --- |
| 内存 | 最低 2GB，实际跑起来 3~4GB | 2G 总内存，业务还要用 |
| 数据库 | PostgreSQL | 没有 |
| 磁盘 | 10GB+ | 40G 还要放镜像 |

**替代方案（覆盖 SonarQube 80% 的价值）**：

| SonarQube 能力 | 免费替代 |
| --- | --- |
| 代码规范 | ESLint / ruff |
| 复杂度/重复代码 | `jscpd`（重复率）、`radon`（Python 复杂度） |
| 覆盖率 | vitest / pytest-cov（已做） |
| 漏洞 | npm audit / pip-audit / Trivy（已做） |
| 新代码质量门禁 | 在 CI 里对比 `git diff` 的文件单独跑检查 |

**如果公司有资源要装**，最小可用配置：

```yaml
services:
  sonar:
    image: sonarqube:10-community
    ports: ["9000:9000"]
    environment:
      - SONAR_ES_BOOTSTRAP_CHECKS_DISABLE=true
    volumes:
      - sonar-data:/opt/sonarqube/data
      - sonar-extensions:/opt/sonarqube/extensions
volumes:
  sonar-data:
  sonar-extensions:
```

> 提醒：单机 2G 内存跑 SonarQube，**一定会 OOM**。至少给 4G，且不要和业务同机。

### 步骤 6 例外流程：给紧急发布留一扇有记录的门

门禁再合理，也会有"必须现在发"的时刻。正确做法不是偷偷绕过，而是**留痕的例外**：

```groovy
parameters {
    booleanParam(name: 'SKIP_SECURITY_SCAN', defaultValue: false, description: '紧急发布跳过安全扫描（需审批）')
}

stage('安全扫描') {
    when { expression { !params.SKIP_SECURITY_SCAN } }
    steps { sh 'bash scripts/security-scan.sh deps' }
}

stage('例外审批') {
    when { expression { params.SKIP_SECURITY_SCAN } }
    steps {
        timeout(time: 30, unit: 'MINUTES') {
            input message: '你正在跳过安全扫描，请填写原因（将记入构建日志）',
                  ok: '我确认，继续发布', submitter: 'admin'
        }
        echo "本次构建跳过了安全扫描，审批人：${env.APPROVER}"
    }
}
```

三个要求：**显式参数、必须审批、日志留痕**。事后复盘能查到"谁在什么时候因为什么跳过了门禁"。

## 四、完整实例：把门禁串进流水线

**文件：`pipelines/jenkins/Jenkinsfile-05-quality`**

```groovy
pipeline {
    agent any

    options {
        timestamps()
        timeout(time: 30, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '30'))
    }

    parameters {
        booleanParam(name: 'SKIP_SECURITY_SCAN', defaultValue: false, description: '紧急发布跳过安全扫描（需审批）')
    }

    stages {
        stage('① 后端测试与覆盖率') {
            steps {
                dir('demos/backend') {
                    sh 'python -m venv .venv'
                    sh '.venv/bin/pip install -r requirements.txt'
                    sh '.venv/bin/pytest'
                }
            }
        }

        stage('② 前端测试与覆盖率') {
            steps {
                dir('demos/frontend') {
                    sh 'npm ci'
                    sh 'npm run lint'
                    sh 'npm run test:cov'
                }
            }
        }

        stage('③ 依赖与密钥扫描') {
            when { expression { !params.SKIP_SECURITY_SCAN } }
            steps {
                sh 'bash scripts/security-scan.sh secrets'
                sh 'bash scripts/security-scan.sh deps'
            }
        }

        stage('④ 构建镜像') {
            steps {
                sh 'docker build -f deploy/Dockerfile.backend -t cicd-demo-backend:${BUILD_NUMBER} demos/backend'
                sh 'docker build -f deploy/Dockerfile.frontend -t cicd-demo-frontend:${BUILD_NUMBER} demos/frontend'
            }
        }

        stage('⑤ 镜像漏洞扫描') {
            when { expression { !params.SKIP_SECURITY_SCAN } }
            steps {
                sh 'bash scripts/security-scan.sh image cicd-demo-backend:${BUILD_NUMBER}'
                sh 'bash scripts/security-scan.sh image cicd-demo-frontend:${BUILD_NUMBER}'
            }
        }

        stage('⑥ 例外审批') {
            when { expression { params.SKIP_SECURITY_SCAN } }
            steps {
                timeout(time: 30, unit: 'MINUTES') {
                    input message: '你正在跳过安全扫描，原因会记入构建日志',
                          ok: '我确认，继续发布', submitter: 'admin'
                }
                echo "本次构建跳过安全扫描，审批人：${env.APPROVER ?: 'unknown'}"
            }
        }
    }

    post {
        failure { echo "门禁未通过：${env.BUILD_URL}console" }
        cleanup { cleanWs() }
    }
}
```

**本地验证（不装 Jenkins 也能跑三道门禁）**：

```powershell
cd I:\work-body-dir\cicd-tutorial

# 1. 密钥扫描（未安装 gitleaks 时会提示跳过，SOFT=1）
$env:SOFT="1"; bash scripts/security-scan.sh secrets

# 2. 依赖扫描
bash scripts/security-scan.sh deps

# 3. 构建并扫描镜像
docker build -f deploy/Dockerfile.backend -t cicd-demo-backend:gate-test demos/backend
bash scripts/security-scan.sh image cicd-demo-backend:gate-test
```

**验证成功的标准**：

- 三道扫描都能跑出明确结论（通过 / 不通过 + 原因）
- 故意在前端代码里写 `const token = "ghp_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"`，`secrets` 扫描应该报出来
- 把 `check-bundle-size.sh` 的阈值改成 1，流水线应立刻变红（证明门禁真的在拦）

## 五、坑与排错

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| `npm audit` 报几十个 moderate，不敢开 | 阈值设太低 | 只拦 `--audit-level=high`，低危定期看 |
| Trivy 每次跑 5 分钟 | 每次都重新下载漏洞库 | 挂载缓存 `~/.cache/trivy`；或用自建镜像源 |
| Trivy 报基础镜像漏洞但无修复版本 | 上游还没修 | `--ignore-unfixed` + 记录 `.trivyignore` |
| gitleaks 误报测试用的假 token | 规则匹配 | 加 `.gitleaksignore`，或在测试里用明显假值 `fake-token-for-test` |
| 覆盖率突然下降导致构建全红 | 新增代码没测试 | 先看报告哪几行没覆盖，补核心分支 |
| 紧急发布被门禁挡住 | 没有例外流程 | 用参数 + 审批（步骤 6），不要直接删门禁 |
| SonarQube 起不来 | 内存不足 | 至少 4G；用 `vm.max_map_count=262144` |
| husky 在 CI 里报错 | `prepare` 脚本找不到 git 目录 | `"prepare": "husky || true"` |
| pre-commit 在 Windows 上路径报错 | 使用了 sh 脚本 | 用 Python 实现的 hook；或改用 ruff 原生 |

## 六、横向对照

| 门禁 | Jenkins | GitHub Actions | GitLab CI |
| --- | --- | --- | --- |
| 提交钩子 | 本地 husky / pre-commit | 同左 | 同左（平台无关） |
| 依赖扫描 | `sh 'npm audit'` | `run: npm audit` 或 Dependabot | `npm audit` + Dependency Scanning |
| 镜像扫描 | Trivy + `--exit-code 1` | `aquasecurity/trivy-action` | `trivy` 模板 |
| 密钥扫描 | gitleaks | `gitleaks/gitleaks-action` | Secret Detection 模板 |
| 覆盖率门禁 | `--cov-fail-under` | 第三方 Action | `coverage:` 正则 |
| 审批例外 | `input submitter` | Environment reviewers | `when: manual` + protected env |

## 七、本章检查清单与练习

### 检查清单

- [ ] 本地提交前会跑 lint（钩子已装，或至少知道怎么装）
- [ ] CI 里 lint / 单测 / 覆盖率三道都阻断
- [ ] `security-scan.sh` 三种模式都能跑
- [ ] 覆盖率阈值有依据（基线法），不是拍脑袋
- [ ] 知道为什么本书不装 SonarQube，以及替代方案
- [ ] 门禁有例外流程（参数 + 审批 + 留痕）

### 练习

**练习 1**：团队现在覆盖率 45%，老板要求三个月内到 80%。给出可执行的推进计划。
<details><summary>参考要点</summary>

① 阈值设 43%（当前 -2%），保证不倒退；② 每次迭代 +3%；③ 只对"新增/修改文件"要求 80%（`git diff --name-only` 过滤）；④ 每周看覆盖率报告，优先补核心业务分支；⑤ 不为覆盖率写假断言。
</details>

**练习 2**：Trivy 报了一个 CRITICAL 漏洞，`Fixed Version` 列是空的。你有三个选择，分别说明适用场景。
<details><summary>参考要点</summary>

① 换基础镜像（如 alpine/distroless）——能消除就最优；② 若该组件实际未使用，记录 `.trivyignore` + 复查日期；③ 临时接受风险 + 加强网络隔离，同时向上游提 issue。绝不"删掉扫描步骤"。
</details>

**练习 3**：为什么 gitleaks 要加 `--redact`？
<details><summary>参考要点</summary>

因为它会把命中的"密钥"内容打印到 CI 日志，而 CI 日志往往有更宽的可见范围（团队成员、第三方集成）。脱敏后只显示位置和规则，避免扫描工具自己变成泄露渠道。
</details>
